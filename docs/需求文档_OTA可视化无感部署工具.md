## 一、工具定位

Windows 端可视化无感部署工具，替代现有 `ota_upgrade_replace.sh` 脚本的 CLI 操作方式，提供图形化界面，支持多包选择、拖拽上传、按流程自动传输替换，适配不同包的操作差异，兼顾稳定性与用户体验。

---

## 二、核心流程总览

```
用户选择/拖拽文件 → 自动识别包类型 → 配置加载 → 文件传输（Win → 工控机 → 板端）
    → 传输前处理（清理/空间检查/备份）
    → 板端操作（解压/赋权/流程映射）
    → 多包顺序执行 + 重启监听
    → 失败时自动回滚
    → 日志记录
```

#### 3.2.2 IP 映射表（继承自脚本）

| 本机（工控机）IP | 板端目标 IP |
|-----------------|------------|
| 172.31.48.102 | 172.31.48.9 |
| 192.168.2.102 | 192.168.2.62 |
| 172.20.1.102 | 172.20.1.22 |
| 192.168.62.102 | 192.168.62.62 |

- 工具启动时自动检测工控机本机 IP，根据映射表自动填充板端 IP

### 3.3 文件传输（Win → 工控机 → 板端）

#### 3.3.1 传输链路

```
[Windows 本机] --(paramiko SFTP)--> [工控机 /tmp/ota_deploy] --(scp)--> [板端 /ota 目录]
```

#### 3.3.2 传输流程

1. **Step 1**：确保工控机临时目录存在（`mkdir -p /tmp/ota_deploy`）
2. **Step 2**：通过 `paramiko` SFTP 将用户选择的 `.zip` 包从 Windows 上传到工控机临时目录，实时更新进度
3. **Step 3**：通过 `paramiko` SSH 在工控机上执行 `scp` 命令，将文件从工控机传输到板端 `/ota` 目录
4. **Step 4**：验证板端文件是否存在
5. **Step 5**：清理工控机临时文件

#### 3.3.3 传输进度反馈

- SFTP 传输时通过 `paramiko` 的 `callback` 函数实时更新界面进度条
- 进度显示格式：`上传到工控机: xxx.zip (已传输/总大小 bytes)`
- 传输完成后显示：`传输完成: xxx.zip`

#### 3.3.4 传输前检查（继承脚本逻辑）

- **空间检查**：通过 `df -Pk /ota` 检查板端 `/ota` 可用空间，需满足 `包大小 + 额外预留空间`
- **空间不足处理**：
  - 弹窗提示用户空间不足
  - 提供"自动清理 `/ota` 目录"选项
  - 清理后重新检查，仍不足则中断并报错
- **备份**：对板端 `/app/<target_dir>` 原目录创建带时间戳的备份到 `/ota/<target_dir>_old_<timestamp>`

### 3.4 板端操作

#### 3.4.1 通用操作

| 操作 | 命令 | 说明 |
|------|------|------|
| **挂载读写** | `mount -o remount rw /app` | 重新挂载为读写模式 |
| **systemd 重载** | `systemctl daemon-reload` | APP 类型升级前执行 |
| **赋权** | `chmod -R 755 <目标目录>` | 递归赋权 |
| **同步** | `sync` | 刷新文件系统缓存 |
| **重启** | `nohup sh -c 'sleep 1; reboot' >/dev/null 2>&1 &` | 后台方式触发重启 |

#### 3.4.2 包类型-操作流程映射表

| 包类型 | 操作流程 | 继承自脚本函数 |
|--------|---------|---------------|
| **app** | ① 挂载读写 → ② daemon-reload → ③ 备份原目录 → ④ `unzip` 解压到 `/app` → ⑤ 删除上传包 → ⑥ `chmod -R 755` 赋权 → ⑦ `sync` → ⑧ `reboot` → ⑨ 监听重启上线 | `upgrade_app_package` |
| **mcu** | ① `ota_tool -p <pkg>:mcu` → ② 不执行 sync/reboot（由 ota_tool 自行管理） | `upgrade_mcu_package` |
| **full** | ① `ota_tool -p <pkg>` → ② SSH 断开（255）视为正常 → ③ 监听重启上线 | `upgrade_full_package` |
| **map** | ① `unzip` 解压 → ② 查找并执行 `map_update.sh9`/`map_update.sh` → ③ `sync` → ④ `reboot` → ⑤ 监听重启上线 | `upgrade_map_package` |

#### 3.4.3 流程监听机制

- **SSH 退出状态监听**：执行远程命令后，监听 SSH 会话退出码
  - `full` 类型：退出码 255（连接中断）视为正常，因板端自动重启
  - 其他异常退出码：视为失败，触发回滚
- **重启确认**：通过循环 SSH 连接测试确认板端重启完成
  - 离线等待：最多 60s（`REBOOT_OFFLINE_WAIT`）
  - 在线等待：最多 300s（`REBOOT_ONLINE_WAIT`）
  - 超时则中断并触发回滚

#### 3.4.4 多包顺序执行

- 多包处理时，按用户选择顺序依次执行
- 前一个包流程完全完成（含重启确认连通）后再启动下一个
- 若某一步失败，自动执行回滚操作

### 3.5 回滚机制

| 触发条件 | 回滚操作 |
|---------|---------|
| 板端操作命令失败 | 将临时备份目录移回原位置：`mv /ota/<backup> /app/<target_dir>` |
| 重启等待超时 | 同上，并弹窗提示 |
| 板端输出匹配错误关键词 | 立即中断当前流程，执行回滚，弹窗提示具体错误 |

- 回滚管理器记录所有备份信息，支持逆序回滚多个备份
- 回滚后记录日志，标记该包升级失败
- 后续包是否继续执行由用户确认（弹窗询问）

### 3.6 日志与异常处理

#### 3.6.1 日志记录

- **日志文件**：所有后台命令输出、板端日志实时写入本地日志文件（按日期命名，如 `deploy_20260610.log`）
- **日志内容**：
  - 时间戳 + 日志级别（DEBUG/INFO/WARN/ERROR/FATAL）
  - 执行的命令及输出
  - 板端返回的原始输出
  - 错误堆栈信息
  - 操作耗时

#### 3.6.2 实时日志显示（主界面）

- 集成在主界面右侧面板
- 功能：
  - **日志级别过滤**：下拉框选择（全部/INFO/WARN/ERROR）
  - **关键词搜索**：输入关键词过滤日志
  - **自动滚动**：实时滚动到最新日志
  - **清空显示**：清空当前日志显示（不清除文件）

#### 3.6.3 独立日志查看器

- 通过界面"日志查看器"按钮打开独立窗口
- 功能：
  - **日志文件列表**：显示所有日志文件及大小
  - **时间筛选**：按日期/时间范围过滤
  - **关键词搜索**：支持输入关键词高亮/过滤
  - **日志级别过滤**：按 DEBUG/INFO/WARN/ERROR 筛选
  - **自动刷新**：每 3 秒自动刷新日志
  - **导出日志**：将筛选后的日志导出为文本文件
  - **清空显示**：清空当前显示

#### 3.6.4 异常监控

- 实时监控板端 SSH 输出，匹配以下错误关键词时立即中断（可在 `package_mapping.json` 配置）：
  - `空间不足` / `No space left`
  - `权限拒绝` / `Permission denied`
  - `未找到` / `No such file` / `not found`
  - `命令未找到` / `command not found`
- 匹配到错误关键词时：
  1. 立即中断当前流程
  2. 执行回滚操作
  3. 弹窗提示具体错误信息
  4. 记录错误日志
